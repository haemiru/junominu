# 블로그 2편 묶음 쓰기 — junominu.com

프로젝트 **1개 → 글 2편**. 한 편만 쓸 거면 `/blog-post` 를 쓴다. 이 스킬은 **재료를 반으로 갈라 두 편을 만드는 것**이 본질이다.

짱샘의 책방 `/add-blog-and-reviews-to-ebook`(글 3편 + 후기)을 이 사이트로 옮긴 것이다. 후기(testimonials)와 댓글은 **여기 없다** — 아래 §1 참고.

---

## 0. 입·출력

- **입력**: ① 대상 프로젝트 slug(없으면 후보를 보여주고 고르게 한다), ② (선택) 강조할 각도·사연.
- **출력**:
  1. `src/posts/YYYY-MM-DD-<slug>-<topic-a>.md` · `src/posts/YYYY-MM-DD-<slug>-<topic-b>.md` — **2개**
  2. 필요 시 `public/shots/` 새 캡처
  3. `public/sitemap.xml` **2줄** 추가
  4. 검증 보고 (글별 자수·이미지·FAQ·JSON-LD, 그리고 빌드)
- **원재료는 반드시 `src/projects.js` 의 `detail`.** 날짜·기능·막힌 점을 **지어내지 말 것**. 없으면 사용자에게 묻는다.

## 1. 원본(책방) 스킬과 다른 점

| 항목 | 원본(책방) | 여기(junominu) |
|---|---|---|
| 글 수 | 3편 | **2편** |
| 저장 | Supabase `blog_posts` (HTML) | **`src/posts/*.md` 파일** — 파일 추가 = 등록 끝 |
| 분량 | 글당 8,000~9,500자 | **글당 2,000~3,000자** |
| 이미지 | Gemini 인포그래픽 9~10장 | **실제 앱 캡처 3~5장** |
| TOC | 필수 | **안 쓴다** — `marked@18` 이 제목에 `id` 를 안 붙여 점프 링크가 죽는다 |
| JSON-LD | 본문에 인라인 | **본문에 넣지 말 것** — 빌드 때 `scripts/prerender-meta.js` 가 심는다(§5) |
| 후기 5~7개 | `testimonials.ts` 에 시드 | **없음** |
| 댓글 | (없음) | **없음 — 백엔드가 없어 저장할 곳이 없다.** 대신 글 하단에 `AskBox`(카톡·이메일)가 자동으로 붙는다(§6) |

> ⚠️ **본문에 `<script type="application/ld+json">` 을 절대 넣지 않는다.** SPA라 크롤러가 보는 건 프리렌더된 정적 HTML이고, 본문 스크립트는 `dangerouslySetInnerHTML` 로 들어가 실행도 노출도 되지 않는다.

## 2. 실행 순서

### 단계 1 — 프로젝트 확정 + 재료 수집

1. `src/projects.js` 에서 대상 프로젝트 객체를 읽는다. slug가 모호하면 후보를 보여주고 고르게 한다.
2. `detail` 에서 뽑아 메모한다 — **이게 두 글의 뼈대다**:
   `started` / `launched`(0 → 배포 N일) · `commits` · `features` · `stack` · `timeline` · `challenges` · `prompts` · `retro`
3. `detail` 이 없으면 글감이 없다 → 사용자에게 알리고 중단하거나 재료를 받아온다.
4. 🔴 **`src/posts/` 를 반드시 먼저 훑는다.** 대부분의 프로젝트는 **이미 글이 1편 있다**(2026-07-23 묶음). 있던 글의 각도·소재·타깃 키워드를 적어 두고 **그 3가지를 모두 피한다.**

### 단계 2 — 🔴 재료 2등분 (이 스킬의 핵심 단계)

**글을 쓰기 전에 재료를 먼저 나눈다.** 이걸 건너뛰면 두 글이 같은 이야기를 두 번 하게 된다 — 이 스킬이 실패하는 유일한 방식이다.

표를 만들어 사용자에게 보여준 뒤 진행한다:

| 재료 | A편 | B편 | 안 씀 |
|---|---|---|---|
| `challenges[0]` 결제 승인 지연 | ✅ | | |
| `challenges[1]` 이미지 용량 | | ✅ | |
| `prompts[0]` | ✅ | | |
| `timeline` 2~4월 | ✅ | | |
| `timeline` 5월~배포 | | ✅ | |

규칙:
- **같은 `challenges` 항목을 두 글에 쓰지 않는다.** 한쪽만 주인이다.
- `features` · `stack` 같은 배경 정보는 양쪽이 **한 문장씩만** 공유해도 된다(중복 아님).
- 재료가 한 덩어리뿐이라 못 나누겠으면 **2편이 무리라고 보고하고 1편만 쓴다.** 억지로 늘리지 않는다.

### 단계 3 — 각도 쌍 정하기

**두 글의 각도는 반드시 서로 달라야 한다.** 재료가 결정한다.

| 쌍 | A편 | B편 | 언제 쓰나 |
|---|---|---|---|
| **A. 삽질 → 방법** (기본) | 막힌 점 → 원인 → 해결 | 재현 가능한 N단계 | `challenges` 와 `prompts` 가 둘 다 두꺼울 때 |
| **B. 결정 → 삽질** | 왜 A 대신 B를 골랐나 | 그 선택 때문에 겪은 문제 | `stack` 선택이 특이할 때 |
| **C. 방법 → 운영** | 어떻게 만들었나 | 배포 후 실제로 벌어진 일 | `launched` 가 있고 운영 데이터가 있을 때 |

- **A편은 문제/사연, B편은 방법/결과** 순서가 기본이다. 읽는 사람이 A에서 걸려 B로 넘어간다.
- 이미 있던 글이 삽질형이면 그 쌍은 못 쓴다 → 다른 쌍으로 튼다.

### 단계 4 — 제목 · 요약 · 키워드 (글마다)

**제목** — 25~35자. 한글은 글자 폭이 넓어 영문 기준(60자)을 쓰면 검색 결과에서 잘린다.
- 핵심 키워드를 **앞 15자 안에**.
- 질문형 / 숫자형 / 반전형 중 하나. 밋밋한 명사 나열 금지.
- 🔴 **두 제목이 같은 패턴이면 안 된다.** 둘 다 숫자형이면 목록에서 한 벌처럼 보인다 — A는 반전형, B는 방법형 식으로 엇갈리게.

**요약(`summary` = 메타 description)** — 70~90자. 검색 결과 아래 줄에 그대로 뜬다.
- 검색 의도 + 핵심 키워드 + 숫자 + "어떻게 됐는지" 한 줄.

**타깃 키워드** — 글마다 1개 + 변형 2개. 🔴 **두 글의 주 키워드가 같으면 안 된다**(같은 검색어에 내 글 둘이 서로 경쟁한다). 제목·요약·첫 문단·H2 하나에 자연스럽게 넣고, 3,000자에 5~7회면 충분하다.

### 단계 5 — 이미지 (글당 3~5장)

1. **`public/shots/` 재사용 우선** — 먼저 목록을 확인하고 주제에 맞는 걸 쓴다.
2. **모자라면 라이브 URL을 새로 캡처**:
   ```powershell
   & "C:\Program Files\Google\Chrome\Application\chrome.exe" --headless --disable-gpu `
     --window-size=1280,800 --hide-scrollbars `
     --screenshot="public/shots/<slug>-<이름>.png" "<프로젝트 URL>"
   ```
   - 파일명 규칙: `<프로젝트slug>-<화면이름>.png`
   - **기존 파일 덮어쓰기 금지.** 있으면 재사용하거나 다른 이름을 쓴다.
   - 🚨 **모바일 폭 캡처에 `--window-size` 를 쓰지 말 것.** 윈도우 크롬은 창 폭 하한(약 500px)이 있어 512px로 렌더한 뒤 PNG만 잘라낸다 → 잘린 그림이 나온다. 모바일이 꼭 필요하면 CDP `Emulation.setDeviceMetricsOverride` 를 쓴다.
   - 로그인·결제 뒤 화면은 캡처가 안 된다 → 그 슬롯은 **빼거나** 사용자에게 캡처를 요청한다. 없는 화면을 지어내지 말 것.
3. **다이어그램은 만들지 않는다.** 흐름 설명이 필요하면 표나 번호 목록으로 대신한다.

**규칙**
- 모든 이미지에 **한국어 alt 25~50자** — 키워드 + 무엇이 보이는 화면인지.
- 히어로(첫 이미지)를 뺀 나머지는 `loading="lazy"`.
- 🔴 **두 글의 첫 이미지를 같은 파일로 쓰지 말 것.** 첫 이미지가 공유 카드(og:image)로 자동 사용되므로(§5), 같으면 스레드·카톡에서 두 글이 구분이 안 된다.

### 단계 6 — 본문 작성 (글마다)

**분량: 한글 2,000~3,000자**(태그·공백·영문 제외). 미달이면 얇은 글, 초과면 이 사이트 톤에 비해 무겁다.

#### 파일 규약
- 경로: `src/posts/YYYY-MM-DD-<post-slug>.md` (오늘 날짜)
- `post-slug`: 영어 kebab-case. **프로젝트 slug 접두사**를 붙인다 (`petphoto-payment-debug`).
- 두 글의 날짜가 같아도 된다. 다만 목록 정렬(`blogData.js`)이 동률일 때 순서를 보장하지 않으므로, **A편을 위에 두고 싶으면 B편 날짜를 하루 앞당긴다.**

#### frontmatter
```markdown
---
title: 제목 25~35자
date: 2026-08-14
summary: 요약 70~90자 — 검색 결과에 그대로 뜬다
tags: [바이브코딩, 삽질기, Supabase]
slug: petphoto-payment-debug
cover: /shots/petphoto-cover.png   # (선택) 없으면 본문 첫 이미지가 자동 사용
---
```
- `tags` 3~5개. 기존 글 태그를 재사용해 묶이게 한다. **두 글이 태그 1~2개는 공유**하되 전부 같게 하지 않는다.
- `date` 는 파일명 날짜와 **반드시 일치**.

#### 본문 구조 (H2 5~6개)
```markdown
<div class="byline">
  <strong>JunoMinu</strong> · 비개발자 출신 1인 메이커 · 22년 IT 경력(시스템 아키텍트)
  <br />AI 바이브 코딩으로 혼자 기획·개발·운영합니다. · 2026년 8월 14일
</div>

![키워드 포함 한국어 alt 25~50자](/shots/xxx.png)

도입 hook 2~3문장. **핵심 키워드를 첫 100자 안에.** 상황을 한 장면으로 던진다.

<div class="answer">
  <strong>한 줄 답</strong>
  <p>결론을 40~80자로 먼저 말한다. AI 검색이 통째로 인용하는 자리다. 숫자·구체어를 넣는다.</p>
</div>

## [H2 #3 — 해결한 순서]
```

#### 본문 체크
- **H1(`#`) 금지.** 제목은 `title` 필드가 `<h1>` 으로 그려진다.
- 🔴 **두 글은 서로를 링크한다.** A편의 「함께 보기」에 B편, B편에 A편. 두 파일을 다 쓴 뒤 slug를 확정하고 양쪽에 넣는다.
- 내부 링크 **2~4개** — `/p/<slug>` 1개(필수) + 짝 글 1개(필수) + `/prompts` 또는 다른 글.
- 외부 링크는 **공식 문서만**(Supabase·React·Vercel 등). 개인 블로그·홍보 글 인용 금지.
- 해시태그 줄 금지(스레드용이다). 분류는 `tags` 필드가 한다.
- 코드 블록은 언어 태그 필수(` ```js `).

### 단계 7 — 구조화 데이터 (자동, 규약만 지키면 됨)

`npm run build` 때 `scripts/prerender-meta.js` 가 `dist/blog/<slug>/index.html` 에 심는다.

| 무엇 | 어디서 오나 | 지켜야 할 것 |
|---|---|---|
| `BlogPosting` | frontmatter 전부 | `title`·`date`·`summary`·`tags` 를 빠짐없이 |
| `og:image` (공유 카드) | `cover` → 없으면 **본문 첫 이미지** | 두 글이 서로 다른 이미지를 쓸 것 |
| `FAQPage` | 본문의 `### Q.` 블록 | **`### Q. 질문` + 바로 아래 문단** 형식, **최소 2개**(3개 권장) |

FAQ가 2개 미만이면 `FAQPage` 는 생성되지 않는다.

### 단계 8 — 저장 · 사이트맵 · 검증

1. **파일 2개 저장**
2. **`public/sitemap.xml` 에 2줄 추가** — 기존 항목과 같은 한 줄 형식:
   ```xml
   <url><loc>https://www.junominu.com/blog/<slug></loc><lastmod>YYYY-MM-DD</lastmod><priority>0.6</priority></url>
   ```
3. **자수 검증 — 글마다** 2,000~3,000자인지 실제로 센다:
   ```bash
   node -e "const fs=require('fs');const s=fs.readFileSync(process.argv[1],'utf8').replace(/^---[\s\S]*?---/,'').replace(/<[^>]+>/g,'').replace(/!\[[^\]]*\]\([^)]*\)/g,'').replace(/\[([^\]]*)\]\([^)]*\)/g,'\$1').replace(/[!-~]/g,'').replace(/\s+/g,'');console.log(s.length+'자')" src/posts/<파일>.md
   ```
   - 미달이면 H2 #2(원인)·#3(순서)·FAQ를 우선 보강. 표·이미지·byline·CTA는 건드리지 않는다.
   - 초과면 H2 #1(배경)을 줄인다.
4. **빌드**: `npm run build` → `dist/blog/<slug>/index.html` **2개**가 생겼는지 확인. 프리렌더 로그의 「글 N」 숫자가 2 늘었는지 본다.
5. **JSON-LD 확인 — 글마다** `application/ld+json` 블록이 1~2개 나오고 JSON이 파싱되는지:
   ```bash
   node -e "const h=require('fs').readFileSync(process.argv[1],'utf8');const b=h.match(/<script type=\"application\/ld\+json\">([\s\S]*?)<\/script>/g)||[];console.log(b.length+'개');b.forEach(x=>JSON.parse(x.replace(/<\/?script[^>]*>/g,'')))" dist/blog/<slug>/index.html
   ```
6. **og:image 가 두 글에서 다른지** 확인 — 같으면 첫 이미지를 바꾼다.
7. **상호 링크 확인** — A편 본문에 `/blog/<B-slug>`, B편 본문에 `/blog/<A-slug>` 가 실제로 있는지.
8. **이미지 존재 확인** — 본문에 쓴 `/shots/...` 가 `public/shots/` 에 실제로 있는지.
9. **lint**: `npm run lint` — 🔴 `Home.jsx` 에 **기존 오류 2건 + 경고 1건**이 있다(2026-08-14 기준). 이 스킬은 `.md` 만 건드리므로 그 숫자가 늘지 않았는지만 본다.

## 3. 작성 보이스

- **1인칭 회고체.** "나는 ~했다 / ~였다" 기본, 설명 구간은 "~합니다" 도 섞는다. 기존 글의 톤을 먼저 읽고 맞춘다.
- **비개발자 독자 기준.** 전문 용어는 처음 나올 때 괄호로 풀어준다. (`환경변수(프로그램이 쓰는 설정값)`)
- **솔직하게.** 막힌 시간, 틀린 판단, 오진을 그대로 쓴다. 이 사이트의 신뢰는 거기서 나온다.
- 문장은 짧게. 한 문장 40자 안쪽 기본.
- 과장 금지. "혁명적인", "완벽한" 대신 숫자를 쓴다.
- 홍보 톤 금지. 제품 자랑이 아니라 **만든 과정의 기록**이다.
- 🔴 **두 글의 도입 hook 패턴을 다르게.** 둘 다 "~라고 생각했다. 그 상태로 N일이 갔다" 로 시작하면 같은 사람이 같은 글을 두 번 쓴 것처럼 보인다.

## 4. 안전 규칙

- **없는 사실을 만들지 않는다.** 날짜·기능·막힌 점은 전부 `src/projects.js` 또는 사용자가 준 것만.
- **재료가 2편을 못 채우면 1편만 쓰고 그렇게 보고한다.** 물로 늘리지 않는다.
- **이미지 덮어쓰기 금지.**
- **같은 slug의 글이 이미 있으면 사용자 확인 후** 덮어쓴다.
- **본문에 JSON-LD `<script>` 넣지 않는다**(§1).
- **본문에 연락처·문의 문구를 쓰지 않는다**(§6 — `AskBox` 가 자동으로 붙어 중복된다).
- `git add` / `git commit` **자동 실행 금지** — 사용자가 결정한다.
- 검증 실패 시 다음으로 강행하지 않고 정확한 에러를 보고한다.
- 캡처가 불가능한 화면(로그인·결제 뒤)은 **빼고** 진행한다.
