# 블로그 글쓰기 — junominu.com

프로젝트 **1개 → 글 1편**(기본) 또는 **2편**(요청 시).

## 🔴 이 블로그의 목적은 **제품 홍보**다 (2026-08-19 확정, 사용자 지시)

이걸 먼저 못 박는다. 예전 이 스킬은 *"제품 자랑이 아니라 만든 과정의 기록"* 이라고 썼는데 **틀렸다.**
그건 목적이 아니라 **수단 중 하나**다.

> **목적**: 읽은 사람이 **"이거 한번 써봐야겠다"** 고 생각하고 **판매처로 넘어가게** 한다.
> **수단**: ① 제품을 바로 소개하거나 ② 만든 과정을 보여줘 신뢰를 쌓거나. 둘 다 같은 목적에 복무한다.

- 🔴 **모든 글은 「무엇을 팔려는 글인지」가 정해진 채로 시작한다**(단계 1-0). 정해지지 않으면 쓰지 않는다.
- 🔴 **제작기를 쓰더라도 그 글이 어느 제품으로 착지하는지가 먼저다.** 착지점 없는 회고는 이 블로그에 안 쓴다.
- **금지되는 건 홍보가 아니라 「과장·거짓」이다.** 없는 기능·부풀린 숫자·"혁명적인" 같은 말을 안 쓸 뿐,
  좋은 점을 또렷하게 말하는 건 이 블로그가 할 일이다.

⚠️ **이미 나간 22편은 소급해서 고치지 않는다**(§5 방침). 앞으로 쓸 글에만 적용한다.

> 📌 **2026-08-19 통합.** 예전엔 `/blog-post`(1편)와 `/add-blogs-to-project`(2편)로 나뉘어 있었는데,
> **규칙이 두 벌이라 계속 어긋났다**(AskBox 규칙이 한쪽에만 있었고, 「라이브 우선」은 하루 뒤에야 따라잡았다).
> 진짜로 다른 건 **단계 2~3(재료 2등분·각도 쌍)뿐**이라 편수 인자로 흡수했다. 🔴 **규칙을 다시 두 파일로 쪼개지 말 것.**
>
> 원본은 짱샘의 책방 `/add-blog-and-reviews-to-ebook`(글 3편 + 후기)이다. 후기·댓글은 여기 없다(§2).

## 0. 입·출력

- **입력**: ① 대상 프로젝트 slug(없으면 후보를 보여주고 고르게 한다), ② **편수**(§1), ③ (선택) 강조할 각도·사연.
- **출력**:
  1. `src/posts/YYYY-MM-DD-<post-slug>.md` — **1편 또는 2편**
  2. 필요 시 `public/shots/` 새 캡처
  3. `public/sitemap.xml` 에 **글 수만큼** URL 추가
  4. 검증 보고(자수·이미지·FAQ·JSON-LD·빌드)
- 🔴 **원재료는 세 곳이다** — ① `src/projects.js` 의 `detail`(목차) ② **그 프로젝트 레포**(단계 1-A)
  ③ 라이브 화면. **어긋나면: 지금 보이는 값은 라이브가, 제작 이야기는 레포가 이긴다**(단계 1-5).
  날짜·기능·막힌 점·가격을 **지어내지 말 것.** 셋 다 없으면 사용자에게 묻는다.
- **어긋난 항목은 「낡은 값」으로 모아 단계 9에서 보고한다** — `detail` 을 고치는 건 사용자 몫이지만, 알려주지 않으면 다음 글도 같은 값으로 틀린다.

- 아래에서 **🔵 [2편]** 표시가 붙은 것만 2편일 때 추가로 한다. 나머지는 편수와 무관하게 똑같다.

- 3편 이상은 지원하지 않는다 — 한 프로젝트에서 각도 3개를 겹치지 않게 뽑기 어렵다. 필요하면 나눠서 두 번 실행한다.

## 3. 실행 순서

### 단계 1 — 프로젝트 확정 + 재료 수집

**단계 1-0 — 🔴 무엇을 팔 글인지 먼저 정한다** (2026-08-19 신설). 이게 안 정해지면 쓰지 않는다.

| 정할 것 | 예 |
|---|---|
| **파는 것** | 브랜드커넥트 도우미 |
| **어디로 보내나** | `https://kmong.com/gig/801624` (상세 없음 → 직결) |
| **살 수 있나** | 지금 판매 중 → **제품형**(단계 3 A). 베타·미출시면 **제작기형**(B) |
| **독자** | 브랜드커넥트 제휴를 받은 블로거 |
| **들어오는 문** | "제휴 상품마다 원고 한 편, 계속 밀린다" ← 제품명이 아니라 **문제** |

1. `src/projects.js` 에서 대상 프로젝트 객체를 읽는다. slug가 모호하면 후보를 보여주고 고르게 한다.
   ⚠️ `url` 이 **판매처**(크몽 gig 등)인 프로젝트가 있다 — 그 링크가 곧 착지점이다.
2. **`detail`** 에서 뽑아 메모한다 — **손으로 적은 요약이라 뼈대가 아니라 목차로 쓴다**:
   `started` / `launched`(0 → 배포 N일) · `commits` · `features` · `stack` · `timeline` ·
   `challenges` · `prompts` · `retro`
3. 🔴 **프로젝트 레포를 훑는다 (§단계 1-A).** ← **제작 이야기의 진짜 출처는 여기다.**
4. 🔴 **`url` 이 있으면 라이브 화면을 캡처해서 읽는다.** 단계 5에서 어차피 이미지를 떠야 하니 순서만 앞당기는 것이다.
   전체 페이지를 길게 뜨고(`--window-size=1280,7000` 정도), 필요하면 잘라서 확대해 문구·숫자·요금을 **눈으로 읽는다.**
   하위 페이지가 있으면 홈 HTML에서 `href="/..."` 를 뽑아 주요 경로도 함께 본다.
5. 🔴 **셋이 어긋나면 아래 순서로 이긴다:**

   | 무엇을 쓸 때 | 이기는 출처 | 왜 |
   |---|---|---|
   | **지금 쓰는 사람이 보는 것** — 요금·개수·화면·문구 | **라이브** | 그게 사실이다 |
   | **왜·어떻게 만들었나** — 막힌 점·결정·커밋 수·날짜 | **레포** | `detail` 은 그 요약일 뿐이고 진짜는 `CLAUDE.md`·git 에 있다 |
   | 나머지 | `detail` | **보조.** 둘 중 하나와 어긋나면 진다 |

   어긋난 항목은 「낡은 값」 목록에 적어 두었다가 **단계 9에서 표로 보고**한다.
6. 셋 다 없으면 글감이 없다 → 사용자에게 알리고 중단하거나 재료를 받아온다.
7. 🔴 **`src/posts/` 를 반드시 먼저 훑는다.** 대부분의 프로젝트는 **이미 글이 1편 이상 있다.**
   나간 글의 **각도·소재·타깃 키워드**를 적어 두고 **그 3가지를 모두 피한다.**
   ```bash
   ls src/posts/ | grep <프로젝트slug>
   grep -h "^title:\|^summary:" src/posts/*<프로젝트slug>*.md
   ```

> **왜 라이브가 이기나 — 두 번 연속 같은 일이 났다(2026-08-14).**
>
> | 프로젝트 | `detail` | 라이브 |
> |---|---|---|
> | 중개프로 | 요금제·기능 구성이 **아예 없음** | Free·14,900·29,900원, 9개 기능, 가입 3단계 |
> | 아이복지모아 | 치료실 **2,270곳**, 보조기기센터 별도 기능 | **5,921곳**, 보조기기센터는 검색에 흡수 |
> | 아이복지모아 | 무료 운영 구조 **기록 없음** | 홈·풋터에 "짱샘의 책방 수익으로 운영" 명시 |
>
> 두 번 다 **글의 뼈대가 `detail` 에 없고 화면에만 있었다.** `detail` 은 사람이 손으로 적는 요약이라 제품이 움직이면 바로 낡는다.
> 라이브를 안 봤으면 낡은 숫자를 그대로 박은 글이 나갔을 것이다.
>
> ⚠️ 대신 **라이브에서 읽은 값(가격·개수·요금제)은 변한다.** 글에 박았으면 단계 9에서 그 사실을 보고해,
> 값이 바뀔 때 어느 글을 고쳐야 하는지 남긴다.

#### 단계 1-A — 🔴 프로젝트 레포 훑기 (2026-08-19 신설, 사용자 지시)

**`detail` + 라이브만으로 쓰면 글이 얇아진다.** 실제로 중개프로 레포를 훑어 보니 `detail` 에
**없거나 틀린 것**이 이만큼 나왔다(2026-08-19):

| | `detail` | 레포 |
|---|---|---|
| 커밋 | 200 | **384** |
| 매물 종목 | 9개 | **10개** |
| AI 회수 · 매물당 사진 · 운영사 | **없음** | Free 10/Basic 150/Pro 500 · 3/10/30장 · 짱샘에듀 |
| 입지분석·시세·공동중개 | **실기능처럼 적혀 있음** | 🔴 **일부 목업** — 세일즈 포인트로 쓰면 안 되는 것 |

반대로 레포에는 **글감이 통째로** 있었다 — 특약 104건, 무효 특약 10개 패턴(강행규정 위반),
토지거래허가구역(서울 25개 자치구), 확인설명서 3종이 계약서 양식에 따라 자동 결정되는 함정.
**`detail` 만 봤으면 하나도 못 썼다.**

**볼 것 — 위에서부터 값이 크다:**

```bash
P=D:/Claude-prj/<폴더>
cat "$P/CLAUDE.md"                                         # ← 최고의 글감
git -C "$P" log --oneline | wc -l                          # 진짜 커밋 수
git -C "$P" log --date=short --format="%ad %s" | tail -40  # 초기 → 지금 흐름
ls "$P/docs" "$P/README.md" 2>/dev/null
head -40 "$P/package.json" 2>/dev/null                     # 진짜 스택
ls "$P/blog-content/context" "$P/naver-blog" 2>/dev/null   # 블로그 자산(아래)
```

- 🔴 **`CLAUDE.md` 가 가장 값지다.** 대개 *"코드를 읽어도 알 수 없는 것 — 함정·확정 결정·
  같이 고쳐야 하는 것"* 만 모아 둔 파일이다. **그게 곧 「막힌 점」·「왜 그렇게 했나」** 라
  삽질형·결정형 글의 본문이 거의 그대로 나온다.
  (있는 곳: `jungaepro` `BokJiMOA` `PetPhotoAI` `dementia-prevention` `Speech-Therapy`
  `kungkung-mate` `SenseTrack` `i-diary` `Detai-Page-Maker` `BrandConnect` —
  ⚠️ `i-talk`·`LLM-Service-Transcripto` 에는 **없다**. 그 둘은 git log·docs 로 대신한다)
- 🔴 **`blog-content/context/product-facts.md` 가 있으면 그게 기능·요금의 단일 근거다**
  (지금은 `jungaepro`·`ebook/jjangsaem-bookshop`). 특히 **「없는 기능」 목록을 반드시 읽고
  거기 있는 걸 글에 쓰지 않는다.** 사람이 관리하는 팩트시트라 `detail` 보다 이게 이긴다.
- ⚠️ **`naver-blog/*.txt` 가 있으면 제목만이라도 훑는다** — 같은 제품을 그쪽 블로그도 쓴다.
  소재가 겹치면 각도를 가른다: **여기는 *내가 왜 그렇게 만들었나*, 거기는 *독자가 무엇을 해야 하나*.**
- **코드를 정독하지 않는다.** 목적은 글감이지 코드 리뷰가 아니다. `CLAUDE.md` → git log → docs

> 🔴 **다른 레포는 읽기만 한다.** 파일을 만들거나 고치지 않고 `git add`·`commit` 도 하지 않는다.

(예: "브랜드커넥트 도우미" ✕ → **"제휴 상품마다 원고 한 편, 계속 밀린다"** ○)

##### A. 제품형 뼈대


|---|---|---|---|
| **삽질형** | `challenges` + 🔴 **레포 `CLAUDE.md` 의 「함정」** 이 구체적일 때 | 막힌 점 → 원인 → 해결 | "결제 연동에서 3일 막혔다 — 원인은 코드가 아니었다" |

```markdown
**함께 보기**
- [<프로젝트> 메이킹 스토리](/p/<slug>) — 이 프로젝트를 만든 전 과정
- [<짝이 되는 글 제목>](/blog/<짝-글-slug>) — 🔵 [2편] 이번에 같이 쓰는 다른 한 편 (**2편일 때 필수**)
- [프롬프트 노트](/prompts) — 실제로 쓴 프롬프트 모음

<div class="post-cta">
  <a href="/p/<slug>">🐾 <프로젝트> 메이킹 스토리 보기 →</a>
</div>
```

🔴 **CTA는 「무엇을 팔 글인지」(단계 1-0)가 정한다.**

| 상황 | CTA |
|---|---|
| **제품형** · 상세 없음 | 판매처 직결 — `<a href="https://kmong.com/gig/801624" target="_blank" rel="noopener">🔗 크몽에서 받기 →</a>` |
| **제품형** · 상세 있음 | `/p/<slug>` (거기 "사이트 열기" 버튼이 판매처로 보낸다) |
| **제작기형** | `/p/<slug>` 메이킹 스토리 |

- 외부 판매처로 보낼 땐 `target="_blank" rel="noopener"` 를 붙인다.
- 「함께 보기」에도 **판매처 한 줄**을 넣을 수 있다(제품형일 때). 본문 1~2회 + CTA 1개가 상한.

#### 본문 체크
- **H1(`#`) 금지.** 제목은 `title` 필드가 `<h1>` 으로 그려진다.
- 내부 링크 **2~4개** — `/p/<slug>` 1개(필수) + `/prompts` 또는 다른 글 1~2개. 🔵 **[2편]이면 짝 글 1개(필수)** 추가.
- 🔵 **[2편] 두 글은 서로를 링크한다.** A편의 「함께 보기」에 B편, B편에 A편. 두 파일을 다 쓴 뒤 slug를 확정하고 양쪽에 넣는다.
- 🔴 **내 제품의 판매처 링크는 넣는다**(크몽 gig·제품 사이트). 이 블로그의 목적이 그것이다.
  `/p/<slug>` 상세가 있으면 **거기를 거쳐** 보내고(머무는 시간이 늘고 신뢰가 붙는다),
  상세가 없으면 **판매처로 직결**한다. 본문 1~2회 + 끝 CTA 1개.
- 그 밖의 외부 링크는 **공식 문서만**(Supabase·React·Vercel 등). 남의 개인 블로그·홍보 글 인용 금지.
- 🔴 **본문에 연락처·"문의 주세요" 문구를 쓰지 않는다**(§7 — `AskBox` 가 자동으로 붙어 두 번 말하게 된다).
- 해시태그 줄 금지(스레드용이다). 분류는 `tags` 필드가 한다.
- 코드 블록은 언어 태그 필수(` ```js `).

### 단계 8 — 저장 · 사이트맵 · 검증

1. **파일 저장** (1편 또는 2편)
2. **`public/sitemap.xml` 에 글 수만큼 줄 추가** — 기존 항목과 같은 한 줄 형식(**파일을 먼저 읽을 것**):

3. **자수 검증 — 글마다** 2,000~3,000자인지 실제로 센다:
   ```bash
   node -e "const fs=require('fs');const s=fs.readFileSync(process.argv[1],'utf8').replace(/^---[\s\S]*?---/,'').replace(/<[^>]+>/g,'').replace(/!\[[^\]]*\]\([^)]*\)/g,'').replace(/\[([^\]]*)\]\([^)]*\)/g,'\$1').replace(/[!-~]/g,'').replace(/\s+/g,'');console.log(s.length+'자')" src/posts/<파일>.md
   ```

   - 미달이면 H2 #2(원인)·#3(순서)·FAQ를 우선 보강. 표·이미지·byline·CTA는 건드리지 않는다.

5. **JSON-LD 확인 — 글마다** `application/ld+json` 블록이 1~2개 나오고 JSON이 파싱되는지:
   ```bash
   node -e "const h=require('fs').readFileSync(process.argv[1],'utf8');const b=h.match(/<script type=\"application\/ld\+json\">([\s\S]*?)<\/script>/g)||[];console.log(b.length+'개');b.forEach(x=>JSON.parse(x.replace(/<\/?script[^>]*>/g,'')))" dist/blog/<slug>/index.html
   ```
6. **이미지 존재 확인** — 본문에 쓴 `/shots/...` 가 `public/shots/` 에 실제로 있는지.
7. 🔵 **[2편] og:image 가 두 글에서 다른지** 확인 — 같으면 첫 이미지를 바꾼다.
8. 🔵 **[2편] 상호 링크 확인** — A편 본문에 `/blog/<B-slug>`, B편 본문에 `/blog/<A-slug>` 가 실제로 있는지.

## 4. 작성 보이스

- **1인칭 회고체.** "나는 ~했다 / ~였다" 기본, 설명 구간은 "~합니다" 도 섞는다. 기존 글의 톤을 먼저 읽고 맞춘다.
- **비개발자 독자 기준.** 전문 용어는 처음 나올 때 괄호로 풀어준다. (`환경변수(프로그램이 쓰는 설정값)`)
- **솔직하게.** 막힌 시간, 틀린 판단, 오진을 그대로 쓴다. 이 사이트의 신뢰는 거기서 나온다.
- 문장은 짧게. 한 문장 40자 안쪽 기본.
- 과장 금지. "혁명적인", "완벽한" 대신 숫자를 쓴다.
- 🔴 **홍보는 목적이다. 금지되는 건 「과장·거짓」이다**(§맨 위, 2026-08-19 개정).
  좋은 점은 또렷하게 쓰되 **없는 기능·부풀린 숫자·"혁명적인/완벽한" 같은 말**을 쓰지 않는다.
  독자가 광고를 알아보고 닫는 건 홍보해서가 아니라 **못 미더워서**다 — 신뢰는 「안 맞는 사람」을 밝히는 데서 나온다.
- 🔵 **[2편] 두 글의 도입 hook 패턴을 다르게.** 둘 다 "~라고 생각했다. 그 상태로 N일이 갔다" 로 시작하면 같은 사람이 같은 글을 두 번 쓴 것처럼 보인다.

## 5. 안전 규칙

- **없는 사실을 만들지 않는다.** 날짜·기능·막힌 점·가격은 `src/projects.js` · **프로젝트 레포** · **라이브 화면** · 사용자가 준 것, 이 넷 중 하나에서 온 것만 쓴다. 넷 다 없으면 묻는다.
- **어긋나면 조용히 넘어가지 않는다.** 지금 보이는 값은 라이브가, 제작 이야기는 레포가 이기고, **어긋난 항목은 단계 9에서 표로 보고한다**(단계 1-5).
- 🔴 **다른 프로젝트 레포는 읽기만 한다**(단계 1-A). 파일 생성·수정 금지, `git add`/`commit` 금지. 산출물은 **junominu 안에만** 만든다 — 레포마다 리모트가 따로다(루트 `CLAUDE.md`).
- 🔴 **레포에 `blog-content/context/product-facts.md` 가 있으면 「없는 기능」 목록을 반드시 읽고, 거기 있는 걸 글에 쓰지 않는다.** 목업을 실기능처럼 쓰면 읽은 사람이 속는다.
- 🔴 **이미 나간 글은 소급해서 고치지 않는다**(사용자 방침 2026-08-18). 앱은 계속 수정되므로 지난 글과 지금 화면이 어긋나는 건 정상이다.
  「낡은 값」은 **앞으로 쓸 글에만** 적용하고, 옛 글을 고칠지는 묻지 않는다 — 물으면 매번 같은 대화를 반복하게 된다.
  예외: 사용자가 직접 고쳐 달라고 할 때, 또는 값이 틀려서 **읽는 사람이 손해를 볼 때**(가격·자격 조건 등).
- 🔵 **[2편] 재료가 2편을 못 채우면 1편만 쓰고 그렇게 보고한다.** 물로 늘리지 않는다.
- **이미지 덮어쓰기 금지.** 같은 이름이 있으면 재사용하거나 다른 이름을 쓴다.
- **같은 slug의 글이 이미 있으면 사용자 확인 후** 덮어쓴다.
- **본문에 JSON-LD `<script>` 넣지 않는다**(§2).
- **본문에 연락처·문의 문구를 쓰지 않는다**(§7 — `AskBox` 가 자동으로 붙어 중복된다).
- `git add` / `git commit` **자동 실행 금지** — 사용자가 결정한다.
- 검증 실패 시 다음으로 강행하지 않고 정확한 에러를 보고한다.
- 캡처가 불가능한 화면(로그인·결제 뒤)은 **빼고** 진행한다. 없는 화면을 지어내지 말 것.

## 8. 글감 확인

로드맵 표를 여기 박아 두면 **금방 낡는다.** 대신 **매번 직접 읽는다**(단계 1-6):

```bash
ls src/posts/                                      # 전체 글
grep -h "^title:" src/posts/*<프로젝트slug>*.md    # 이 프로젝트로 나간 글의 각도
```

- 프로젝트마다 이미 1편 이상 나가 있다. **나간 각도를 피해서** 새 각도를 잡는다.
- `detail` 이 없는 프로젝트는 상세 페이지(`/p/<slug>`)도 없다 → 「함께 보기」의 `/p/<slug>` 링크를 넣을 수 없으니 그 줄을 뺀다.
